# Прошивка и приёмочное чтение

[English version](../en/06-flashing.md). Сначала прочитать
[../../SAFETY.ru.md](../../SAFETY.ru.md).

Всё ниже делается через ADFU, одним процессом, с чтением обратно до того, как вынут кабель. Правка
зерна (`use_hw_seed()`) применяется автоматически; без неё запись даёт устройство, которое не
загружается.

## Три шага

```bash
cd /путь/к/ats2819-notes

# 1. сухой прогон: ADFUS + HWSC + инициализация FWSC, без записи
sudo .venv/bin/python tools/adfu_flash.py stock
#    ожидаем: flash id c84015, FWSC init status 0

# 2. запись с проверкой в той же USB-сессии
echo WRITE | sudo .venv/bin/python tools/adfu_flash.py ours --write --verify 0x5000
#    ожидаем: BREC ok, LFI ok, MBREC ok, ~8 с, затем 20480/20480 IDENTICAL

# 3. отключить кабель, подключить, включить наушники
```

`stock` пишет заводской образ из `firmware/stock/nor_logical_1MB.bin`; `ours` пишет
`firmware/prompts-ru-en/afi_plain.bin` или свежесобранный `build/fw/afi_plain.bin`, если он есть.
Подтверждение на вводе сделано намеренно: для записи нужно слово `WRITE`.

Одна строка в выводе говорит, что правка зерна встала. Если её нет — остановиться:

```
NorFwsc patched at 0xbfc2c308: RAND_SEL not set, write uses the eFuse seed
```

## Приёмочное чтение — в нём весь смысл

Единственная честная проверка — прочитать флеш **тем же путём, которым его читает процессор**:
через кэш, с рандомайзером на встроенном зерне чипа, — и сравнить с образом. Это `--verify` при
записи и `--xip2` как отдельная команда только для чтения:

```bash
sudo .venv/bin/python tools/adfu_flash.py stock --xip2 0 0x5000
```

Критерий — одна строка:

```
matches factory image: 20480/20480  -- IDENTICAL
```

Если совпало — загрузочное ПЗУ прочитает те же байты, потому что это тот же путь. Если не совпало,
**не надо переподключать и надеяться** — сначала разобраться.

`--seed 0` заставляет читать с программным зерном 0. Образ, который читается с `--seed 0`, но не
читается без него, записан старым, сломанным способом — это подпись той самой ошибки, описанной в
[07-recovery.md](07-recovery.md).

### Как честно читать вывод

* **Флаг ошибки CRC во время приёмочного чтения — это норма.** Промежуток `0x400`–`0xFC0` стёрт,
  его контрольные байты `FF FF`, и они не совпадают ни с какой CRC. Судить надо по сравнению байт,
  а не по флагу.
* **Сверка с собственной моделью формата не доказывает ничего.** `tools/verify_raw.py` строит
  словарь строк по нашему же прежнему дампу, поэтому он показал «14 476 строк, 0 расхождений» на
  образе, который устройство не могло загрузить. Он годится для проверки *повторяемости* записи, но
  не её *правильности*. То же относится к `tools/norline.py`.
* **Один процесс, одна сессия.** Не снимать чтение вторым запуском, см. [05-adfu.md](05-adfu.md).

## Как выглядел успешный прогон

Запись, после которой наушники заговорили по-русски:

```
echo WRITE | .venv/bin/python tools/adfu_flash.py ours --write --verify 0x5000
  ADFUS ok, flash c84015, FWSC init status 0
  write 8.4 s
  20480/20480 IDENTICAL    VERDICT PASS
```

Затем переподключение, включение — и устройство говорит по-русски. У записанного образа LFI
размером `0xE9900` байт, кончается на логическом `0xEDB80` (предел `0xF0000`, то есть запас около
9 КБ), и он на 47 424 байта больше заводского — всё это `TTS_RC.LIB`.

## Альтернатива: обновление с диска

Положить `UPGRADE.HEX` в корень собственного диска `AGP-S22` и выключить-включить: прошивка
обновит себя сама. Не нужен ни сервисный режим, ни `sudo`, ни игры с кабелем — и **нет никакой
проверки до записи**, а запускается загрузчик FWSC, лежащий внутри пакета. Это не более безопасный
путь. Что пакету нужно, чтобы ему можно было доверять, — в [04-fwu-format.md](04-fwu-format.md).
