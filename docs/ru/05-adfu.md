# ADFU: протокол, загрузчики и чтение флеша без записи

[English version](../en/05-adfu.md). Полные черновые записи:
[../../notes/RE_NOTES.md](../../notes/RE_NOTES.md).

## Команды самого загрузочного ПЗУ

ADFU устроен как USB-накопитель: команды в CBW, ответы в CSW, данные по bulk-каналам. Каналы надо
**определять автоматически** — те, которые сообщает это устройство, не совпадают с 0x02/0x81,
заложенными в инструменты «по умолчанию»; это и правит
`patches/actions-adfu-endpoints.patch`.

Переход в ADFU из режима диска: опрос `0xCC` → ответ `ACTIONSUSBD`, затем команда `0xCB`. После
этого ПЗУ видно как `10d6:10d6`, и на опрос оно отвечает строкой `\x00CADFUD\x18QA\x00`.

| CBW | Что делает |
|---|---|
| `0xCD 0x93` | чтение памяти |
| `0xCD 0x13` | запись в ОЗУ |
| `0xCD 0x20` | запуск кода с адреса |

**Чтение памяти через ПЗУ идёт побайтно.** Обычная память читается верно, а 32-битный регистр
периферии отдаёт только младший байт. Отсюда две запомнившиеся путаницы: «живое `CTL = 0x38`» —
это младший байт настоящего `0x00361838`, а «`SPI0+0x20 = 0x80`» — младший байт `0x001E0F80`.
Регистры надо читать своим кодом, через `lw` — `tools/adfu_flash.py --regs`.

## Своя программа в ОЗУ

`tools/adfu_stub.py` загружает в ОЗУ устройства небольшую программу на MIPS32 командой `0x13`,
запускает её командой `0x20`, и программа **возвращается в командный цикл ADFU по `0xbfc040ed`**
вместо завершения. Поэтому устройство остаётся в сервисном режиме, а USB-сессия выживает. Стаб
делает настоящие 32-битные чтения и записи, то есть умеет читать регистры и может занять запись
отображения флеша, чтобы прочитать любой участок через окно XIP.

Два урока, оплаченных временем:

* **Использовать запись отображения 0.** ПЗУ уже отобразило запись 0 на виртуальный `0x02000000`.
  Если занять «свободную» запись 9 под тот же виртуальный адрес, получится два отображения на один
  адрес, и читается не то, что просили.
* **Восстанавливать то, что изменили загрузчики.** HWSC и FWSC перенастраивают SPI0; стаб
  восстанавливает SPI0 и регистры отображения по ранее прочитанным значениям и возвращается в ПЗУ,
  так что окно XIP продолжает работать.

## Заводские загрузчики и что им позволено

| Загрузчик | Адрес загрузки | Точки входа |
|---|---|---|
| `ADFUS.BIN` | `0xbfc28000` | свой диспетчер команд |
| `NorHwsc.bin` | `0xbfc2c000` | смещение 0: определить чип флеша |
| `NorFwsc.bin` | `0xbfc2c000` | `+0x200` инициализация, `+0x400` драйвер записи |

HWSC и FWSC делят один слот и работают в разных проходах. ADFUS заранее ставит свой указатель на
драйвер (`0xbfc28bbc`) в `0xbfc2c400`.

### Диспетчер ADFUS

`cb[0] = 0xCD` выбирает вендорские команды (`0xB0` — сброс); `cb[1] & 0x7F` — подкоманда,
`cb[1] & 0x80` помечает направление IN:

| Подкоманда | Обработчик | Назначение |
|---|---|---|
| `0x10` | `0xbfc28661` | RW_PHY — путь во флеш, см. ниже |
| `0x13` | `0xbfc284a5` | запись в ОЗУ (чтения `0x93`) |
| `0x20` | `0xbfc28511` | SWITCH |
| `0x21` | `0xbfc28561` | CALL_ENTRY — вызов адреса без аргументов, возврат сохраняется |
| `0x22` | | POLL |
| `0x23` | | GET_STATUS — отдаёт байты по сохранённому указателю |
| `0x60` | `0xbfc28775` | DOWNLOAD_IMAGE |

В обработчике `0x10`: `mode = addr >> 24`, `addr &= 0xFFFFFF`, данные идут куска́ми до 8 КБ через
`0x9fc20000`. Режим `0xFF` вызывает `drv(0xFF,0,0,0)`; режим с битом `0x40` сначала принимает
данные OUT, потом вызывает драйвер (это путь записи); любой другой режим вызывает драйвер, а затем
**отдаёт** буфер в направлении IN — единственный путь, похожий на чтение.

### Режимы драйвера FWSC — и почему `0x10` никогда не чтение

| Режим | Что драйвер делает на самом деле |
|---|---|
| `0xFF` | ничего, возвращает 0 |
| `0x80` (бит 0x80 без 0x40) | ничего; ADFUS отдаёт то, что лежит в буфере ОЗУ |
| `0xC0` | запись LFI; первый вызов ещё и подготавливает область |
| младший полубайт 0 (`0x00`, `0x40`) | **запись MBREC**, сектор 0, подпись `0x1234` |
| младший полубайт 6 (`0x06`, `0x46`) | **запись BREC** по +1024 |

**Режима чтения нет.** Режимы `0x00` и `0x06` выполняют *запись* даже когда посланы в направлении
IN. Послать такой режим «на чтение» — значит затереть загрузочные записи содержимым буфера.

Хуже: `NorFwsc.bin`, извлечённый из заводского `AFI.bin`, при **первом** вызове драйвера в
**любом** режиме, включая `0x80` и `0xFF`, стирает NOR `0x0000`–`0xFFFF`, а при `header[2] == 2`
стирает весь чип ещё на инициализации. Правило «`0x80`/`0xFF` безвредны» верно только для более
простого `Fwsc.bin` из производственного каталога SDK. Считайте любой вызов драйвера записью.

Безопасные шаги, таким образом: загрузить ADFUS и SWITCH; вызвать HWSC и GET_STATUS (только
определение чипа); вызвать инициализацию FWSC и GET_STATUS. Команды «только прочитать NOR» у
заводской пары **нет вообще**.

## Как всё-таки прочитать флеш, три способа

1. **Через ПЗУ, по окну XIP.** `tools/adfu_core.py` читает `0x10000000` командой `0x93`. Просто и
   безопасно, но окно начинается с того логического смещения, которое стоит в отображении (на
   работающей прошивке — `0x5980`), так что загрузочных записей в нём нет.
2. **Через стаб и запись отображения 0.** `tools/adfu_stub.py mapat <phys> <len>` направляет
   отображение на любое смещение и читает его. Именно так был снят первый мегабайт вместе с
   загрузочными записями.
3. **Сырое чтение SPI через собственную операцию загрузчика.** Запись 0 таблицы операций
   `NorFwsc` по адресу `0xbfc2d065` — это обычный `read(phys, buf, len)` командой SPI `0x0B`,
   возвращающий *физические* байты: строки, CRC и перемешивание включительно. Используется в
   `tools/adfu_flash.py --read PHY LEN`. Это единственный способ увидеть, что реально лежит на
   чипе, и так снят `firmware/raw/raw_first_1MB.bin`.

Чтение тем путём, которым читает **процессор** — через кэш, с проверкой CRC и рандомайзером, —
это `--xip2`, см. [02-flash-format.md](02-flash-format.md). Только оно отвечает на вопрос «сможет
ли загрузочное ПЗУ это прочитать?».

## Два операционных урока

* **Не разбивать один заход в ADFU на два запуска инструмента.** После длинного чтения USB-сессия
  непригодна, и новый процесс её не поднимает: `CSW status 2`, затем `Overflow`, затем
  `Pipe error`, затем таймаут. Всё, что должно произойти за один заход, должно идти одним
  процессом — для этого у `--write` есть `--verify`, который читает обратно в той же сессии.
* **Исправное устройство выходит из программно включённого ADFU само** за секунды. Пока прошивка не
  загружалась, устройство висело в ADFU бесконечно, и режим казался стабильным. Чтобы поймать
  работающее устройство, надо опрашивать USB на появление `10d6:10d6` и начинать в тот же момент.
* После прогона, завершившегося командой `OVER`, устройство не отвечает на опрос ПЗУ до
  переподключения кабеля. `start_adfus()` в этом случае переиспользует уже загруженный ADFUS, а не
  пишет поверх работающего кода.
