# Устройство

Наушники (гарнитура) с **костной проводимостью**. На корпусе и в Bluetooth — имя **B18**, по USB
появляются как флеш-диск **AGP-S22**. Как изделие называется в продаже — неизвестно: марки на
устройстве нет, строка серийного номера в дескрипторе USB пустая, и единственные имена, которые оно
сообщает, — вот эти два. `AGP-S22` похоже на модельный код производителя, но чей он, по железу не
определить. [English version](../en/01-device.md).

## Идентификаторы

**Bluetooth.** Имя `B18`, класс Headset. Младшие три байта адреса — это LAP, и он есть в заголовке
прошивки (`bt_lap`, см. [03-firmware-layout.md](03-firmware-layout.md)), — но на этом экземпляре в
заголовке стоит *другой* LAP, не тот, который устройство объявляет. Настоящий адрес берётся из
отдельной области чипа, то есть MAC в образе прошивки не «зашит» буквально.

**USB (режим диска).** `10d6:1101`, производитель `ACTIONS`, продукт `AGP-S22`, версия устройства
`0x0100`. Дескриптор серийного номера есть (индекс 3), но строка **пустая**. Диск — FAT32, 8 ГБ,
один раздел MBR с меткой `AGP-S22`, на нём пользовательские mp3; файлов прошивки нет.

## Тот ли у вас чип?

Три дешёвые проверки, в порядке убедительности:

1. **Формат `tts_rc.lib`.** Снять дамп флеша (`tools/adfu_stub.py mapat`, только чтение), вынуть
   из него файлы самой прошивки командой `tools/lfi_extract.py IMAGE.bin OUT_DIR` и посмотреть
   первые 16 байт `TTS_RC.LIB`: `MP3 `, частота, размер кадра, затем литерал `v2  `. Это формат
   эпохи US281B. Та же команда даёт `CONFIG.BIN`, который нужен следующей проверке.
2. **Идентификаторы конфигурации 17–21** (`FACTORY_FW_INFO_*`), прочитанные `tools/cfgdump.py`, —
   именно по ним здесь и была опознана платформа, совпадением с открытым SDK
   [github.com/Pachouli/2819p](https://github.com/Pachouli/2819p).
3. **Чип флеша**, который сообщает загрузчик HWSC: `C8 40 15`, GigaDevice GD25Q16, 2 МБ.

Если что-то из этого отличается — считайте все адреса в этом репозитории предположениями.

## Голосовые подсказки

В прошивке **31 китайская подсказка и ни одной английской**. Переключить язык кнопками или
настройкой нельзя: в `tts_rc.lib` есть слоты под второй язык, и они пустые. Единственный путь к
другому языку — заменить сами файлы подсказок, см. [08-custom-prompts.md](08-custom-prompts.md).

Подсказки — MP3, 16 кГц, 16 кбит/с, моно. Все 31 заводской клип побайтно совпали с файлами из SDK —
отсюда точно известен смысл каждого.

## Сервисный режим ADFU

У чипов Actions есть сервисный режим загрузочного ПЗУ — **ADFU**, через который память читается и
пишется без участия прошивки.

* Обычный режим (диск): `10d6:1101`.
* Загрузочное ПЗУ: `10d6:10d6`. На опрос отвечает строкой `\x00CADFUD\x18QA\x00`.
* Переход в ADFU: опрос `0xCC` → ответ `ACTIONSUSBD`, затем команда `0xCB`. Реализовано в
  [actions-adfu](https://github.com/sonigeez/actions-adfu) плюс
  `patches/actions-adfu-endpoints.patch`, который добавляет автоопределение bulk-каналов.
* Выход из ADFU: отключить и снова подключить кабель. **Но исправное устройство выходит из ADFU и
  само**, через несколько секунд простоя. Пока прошивка не загружалась, оно висело в ADFU
  бесконечно — отсюда ложное впечатление, что режим стабилен. Чтобы поймать исправное устройство,
  скрипт-«ловушка» должен ждать появления `10d6:10d6` и начинать работу в тот же момент.
* **В ADFU не идёт зарядка.** Несколько часов в сервисном режиме посадили аккумулятор до
  срабатывания защиты: устройство перестало включаться вовсе, и помогла только долгая зарядка.
* Переключение в ADFU из обычного режима требует `sudo`: macOS держит драйвер накопителя, его надо
  отцепить. Перед этим том стоит размонтировать (`diskutil unmount /Volumes/AGP-S22`).

### Как по USB понять состояние устройства

| Что видно | Что это значит |
|---|---|
| `10d6:1101` и диск `AGP-S22` | прошивка работает |
| `10d6:10d6` | ПЗУ не смогло запустить прошивку — во флеше нет пригодной загрузки |
| ничего, горит красный индикатор | устройство выключено и заряжается, **либо** глубокий разряд |

Третья строка важна: у исправных наушников подключение кабеля в выключенном состоянии **не даёт
никакого устройства на USB**, только заряд. Это не поломка. А вот `10d6:10d6` — надёжный признак
того, что прошивка не загружается.

### Команды загрузочного ПЗУ, которыми здесь пользовались

* `0xCD 0x93` — чтение памяти;
* `0xCD 0x13` — запись в ОЗУ;
* `0xCD 0x20` — запуск кода с адреса.

Одна особенность определяет всё остальное: чтение памяти через ПЗУ идёт **побайтно**. Обычная
память читается верно, а 32-битные регистры периферии возвращают мусор. Поэтому для чтения
регистров отображения флеша понадобилась своя программа на MIPS — см. [05-adfu.md](05-adfu.md).

## Инструменты здесь

* `tools/adfu_core.py` — доступ по ADFU и чтение отображённого флеша через ПЗУ.
* `tools/adfu_stub.py` — запуск маленьких программ на MIPS32 в ОЗУ устройства (чтение регистров,
  перенастройка отображения, проверка загрузчиков). Пишет только в ОЗУ, не во флеш.
* `tools/adfu_flash.py` — запись и, что важнее, чтение: `--read` (сырое физическое), `--xip2`
  (через кэш, как читает процессор), `--regs` (регистры через `lw`).
* `tools/extract_all.py` — чтение всего, до чего достаёт команда чтения ПЗУ, без записи.

Всё, что работает с USB, запускается с `sudo`, например
`sudo .venv/bin/python tools/adfu_stub.py regs`.
