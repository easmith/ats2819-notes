# Чип и как данные физически лежат во флеше

Самое важное место во всём репозитории: **логический вид прошивки и содержимое микросхемы — это
разные байты.** [English version](../en/02-flash-format.md).

## Платформа

Наушники построены на SoC Actions **ATS2819** семейства **US281B**. Определено совпадением
идентификаторов конфигурации (`FACTORY_FW_INFO_*`) с открытым SDK
[github.com/Pachouli/2819p](https://github.com/Pachouli/2819p) и подтверждено разбором загрузочного
ПЗУ и загрузчиков самого устройства.

Ядро — **MIPS**, смесь MIPS32 и MIPS16 с переключением наборов команд. Загрузочное ПЗУ подписано
строкой `UCOS @Actions`. Загрузчики и объектные файлы SDK — в основном MIPS16:

```bash
/opt/homebrew/opt/binutils/bin/gobjdump -d -m mips:isa32 файл.o     # MIPS16 понимает
```

Capstone MIPS16 **не поддерживает**, только MIPS32. Рассчитывайте на `gobjdump`.

## Карта адресов

Адресация MIPS: `0x8xxxxxxx` — кэшируемая (kseg0), `0xaxxxxxxx`/`0xbxxxxxxx` — некэшируемая
(kseg1); один и тот же физический адрес виден через оба окна.

| Адрес | Что это |
|---|---|
| `0x10000000` | Окно отображения флеша (XIP) — через него прошивка исполняется и читается |
| `0x02000000` | Окно, которое настраивает само ПЗУ (запись 0 отображения) |
| `0xbfc00000` | Загрузочное ПЗУ (~32 КБ) и встроенное ОЗУ |
| `0xbfc28000` | Куда штатный инструмент грузит загрузчик ADFUS |
| `0xbfc2c000` | Куда грузятся HWSC и FWSC (делят слот, работают по очереди) |
| `0xbfc040ed` | Точка входа командного цикла ADFU в ПЗУ (MIPS16) |
| `0xbfc45ff0` | Вершина стека ПЗУ |
| `0x9fc3a000` | Куда прошивка грузит `upgrade.bin` при обновлении с диска |
| `0xc0000000` | RMU, сбросы модулей (бит 6 — SPI0, бит 14 — кэш SPI) |
| `0xc0001028` | `CMU_SPICLK` |
| `0xc0001064` | `CMU_MEMCLKEN`, в том числе ОЗУ кэша SPI |
| `0xc00a0000` | Контроллер отображения флеша (MMU), 16 записей |
| `0xc0110000` | Регистры контроллера SPI0 |
| `0xc0120000` | Сторожевой таймер (`+0x1C`) и прочее |
| `0xc0140000` | Контроллер кэша SPI: включение, сброс, границы области CRC |

## Микросхема флеша

**GD25Q16** (GigaDevice), JEDEC-идентификатор `C8 40 15`, **2 МБ**, на SPI0. Чтение командами
`0x0B`/`0x3B`/`0x6B` (fast read), стирание блока `0xD8`, сектора `0x20`, запись страницы `0x02`.
Определена на устройстве загрузчиком HWSC; совпало и с BREC наушников, и с таблицей `nor_id.bin`
из SDK.

## Две области, два формата хранения

| Физические адреса | Как хранится | Что там |
|---|---|---|
| `0x000000` … `0x1F0000` | строками: 64 байта данных + 2 байта CRC = **66 байт** | прошивка |
| `0x1F0000` … `0x200000` | **как есть, 1:1**, без строк и преобразований | VRAM: настройки, сопряжения |

Отсюда логическая ёмкость области прошивки: `(0x1F0000 / 66) × 64 = 30782 × 64 = 0x1E0F80`, а
адреса пересчитываются как `физический = (логический / 64) × 66 + (логический mod 64)`.

Размер зарезервированного «хвоста» — не поле заголовка, а **константа в BREC**: литерал
`0xFFFF0000` (ёмкость минус `0x10000`) по смещению `0x21A4` логического образа. Последняя полная
строка кончается на `0x1EFFBC`, остаток 68 байт не используется.

Два независимых подтверждения:

1. **По данным.** Записи сопряжений в хвостовой области видны в сыром чтении **открытым текстом**,
   и разница между физическим и логическим адресом там постоянна и равна `0xF07C = 0x1E0F80 / 32`.
2. **По регистрам.** После инициализации FWSC `SPI0+0x20` и `0xC0140008` содержат ровно
   `0x001E0F80`.

### Два байта CRC

Считаются **программно** (в загрузчике по адресу `0xbfc2f6a1`): CRC16, полином `0x1021`, начальное
значение `0xFFFF`, биты данных младшим вперёд, результат с перестановкой байт, хранится младшим
байтом вперёд. Для строки из 64 нулей получается `0xDAD6`.

Проверяет их **аппаратура и только на кэш-пути (XIP)** — так прямо написано в даташите: «Support
16bit CRC only when Cache access fifo». При несовпадении кэш отдаёт `0xFF` на всю строку и
поднимает флаг ошибки. Поэтому стёртая область при чтении через кэш **всегда** даёт ошибку CRC
(`FF FF` не совпадает ни с какой суммой). Это нормально, а не признак поломки.

### Рандомайзер и зерно — та самая ловушка

64 байта данных каждой строки проходят через **аппаратный рандомайзер** контроллера SPI0.
Преобразование самообратное, зависит только от содержимого строки и сбрасывается на каждой строке:

```
stored[k] = plain[k] XOR F(stored[k-1], stored[k-2], stored[k-3])
```

`F` нелинейна — линейные скремблеры до 64 отводов не подходят ни в одном порядке бит, — и её
таблица в кремнии. Начальное состояние задаётся **зерном**, и вот откуда оно берётся:

* `CTL` бит 14 (`RAND_SEL`) **установлен** → зерно читается из регистра `SPI0+0x14` (программное);
* бит 14 **сброшен** → используется **встроенное зерно чипа** из eFuse.

**Зерно — это CHIPID микросхемы.** Заводской скрипт сборки заполняет таблицу `chipid_data`
(36 слов по смещению `+240` в заголовке FWSC) случайными значениями для маскировки и прячет
настоящее `CHIPID | package_id` по индексу `chipid_data[35] % 35`. Инициализация `NorFwsc`
(`0xbfc2c2b8`…`0xbfc2c36c`) делает:

```
t8 = 0xC0110000
CTL |= 0x4000                       ; взять зерно из регистра
[0xC0110014] = header[240 + idx*4]  ; idx = header[380] % 35, с проверкой чтением
```

**Загрузочное ПЗУ читает флеш с битом 14 сброшенным и никогда не пишет `SPI0+0x14`** — то есть со
встроенным зерном. Его `CTL` при чтении MBREC: `0x0018120A` (`CRC_EN` есть, `RAND_RXEN` есть, бит
14 сброшен). Установлено перечислением всех 25 обращений к `CTL` во всём ПЗУ.

**Как это ломает устройство.** В поставляемом `NorFwsc.bin` таблица по `+240` нулевая. Значит
загрузчик пишет прошивку, перемешанную **нулевым** зерном, ПЗУ потом расшифровывает её встроенным,
видит шум, не находит MBREC и уходит в ADFU. Именно так эти наушники были сломаны 25 октября 2026
года.

**Лечение** — одно слово в загружаемой копии загрузчика:

```
0xBFC2C308 (смещение 0x308 в NorFwsc.bin):  0x34794000  ->  0x34790000
            ori t9,v1,0x4000                ori t9,v1,0
```

Реализовано как `use_hw_seed()` в `tools/adfu_flash.py`, применяется **по умолчанию** (отключается
флагом `--sw-seed`, который и есть режим «сломать устройство»). Запись самого регистра зерна и
её проверка чтением оставлены на месте, чтобы инициализация по-прежнему возвращала статус 0.

В пишущей части загрузчика есть **второе** место с битом 14 — `0xbfc2faca` (`CTL |= 0x6000`), — но
оно под условием на флаг по адресу `0xbfc2fc60`, которое здесь не выполняется. При правках этого
пути о нём надо помнить.

> Прежний вывод «на этом экземпляре шифрование выключено, `decrypt_mode = 0` в BREC, ключ не
> нужен» — **неверен**, и именно он привёл к поломке. Поле `decrypt_mode` относится к другому
> механизму. Аппаратный рандомайзер работает всегда, и его зерно — CHIPID.

## Регистры SPI0 (`0xC0110000`)

| Смещение | Назначение |
|---|---|
| `+0x00` | `CTL` |
| `+0x04` | `STATUS` |
| `+0x08` | `TXDAT` |
| `+0x0C` | `RXDAT` |
| `+0x10` | `BC`, счётчик байт |
| `+0x14` | `SEED`, 32-битное зерно рандомайзера |
| `+0x18` | логический адрес строки, на которой зафиксирована ошибка CRC |
| `+0x1C` | `CACHE_MODE` |
| `+0x20` | логический конец области CRC (здесь `0x001E0F80`) |

Биты `CTL`:

| Бит | Имя | Смысл |
|---|---|---|
| 29 | `NO_CRC_RAND_RXEN` | рандомайзер чтения для «сырой» области |
| 21 | `CRC_IRQ_EN` | прерывание по ошибке CRC |
| 20 | `CRC_EN` | проверка CRC строк |
| 16–19 | `SPI_DELAY` | цепочка задержки |
| 15 | `RAND_PAUSE` | пауза рандомайзера |
| 14 | `RAND_SEL` | брать зерно из `+0x14`, а не встроенное |
| 13 | `RAND_TXEN` | рандомайзер записи |
| 12 | `RAND_RXEN` | рандомайзер чтения |
| 8 | `SPI_REQ` | процессор забирает FIFO у кэша |
| 5, 4 | FIFO | включение передающего / принимающего FIFO |
| 3 | `SS` | выбор кристалла |

Биты `STATUS`: 8 — `SPI_READY`, **7 — ошибка CRC кэша** (сбрасывается записью `0x80`), 1 —
`CRC_ERROR`.

Контроллер кэша `0xC0140000`: бит 0 — включение, **бит 2 — «сырой» режим в обход декодирования**
(его выставляет инициализация FWSC, отсюда `1` на холодную и `5` после инициализации).
`0xC0140004 = 1` — сброс кэша, бит снимается сам, надо дождаться. `0xC0140008` — логический размер
области CRC, `0xC014000C` — константа `0x003FFFC0`.

## Отображение флеша в память (XIP)

Флеш не копируется в ОЗУ — он **отображается** через контроллер кэша (`0xc00a0000`), у которого
**16 записей**, каждая из пары 32-битных слов:

* слово отображения по `0xc00a0090 + 8·i`: `0x40000000 | виртуальный базовый адрес`;
* второе слово по `0xc00a0094 + 8·i`: **логическое** смещение в прошивке, а не физическое.

Что второе слово логическое — доказано: у работавшей прошивки запись 1 содержала `0x5980`, и
содержимое окна `0x10000000` начинается ровно со смещения `0x5980` логического образа. Пересчёт
адреса и декодирование строк делает сама аппаратура.

**Загрузочное ПЗУ занимает запись 0** и отображает её на виртуальный `0x02000000`. Для своих чтений
надо использовать **запись 0**, а не «свободную» запись 9: иначе два отображения указывают на один
виртуальный адрес и читается не то, что задумано. На этом здесь было потеряно время.

### Как правильно прочитать флеш с декодированием

Последовательность снята с `hal_spi_phy_init` из SDK
(`vendor/2819p/psp_rel/HAL/lib/hal_spi_phy_init.o`) и реализована в `tools/adfu_flash.py --xip2`:

```c
[0xC0001064] = 0x001FFFFF;            // CMU_MEMCLKEN, в том числе ОЗУ кэша
[0xC0001028] = 0x40;                  // CMU_SPICLK
[0xC0000000] &= ~0x40;  |= 0x40;      // сброс SPI0
[0xC0000000] &= ~0x4000; |= 0x4000;   // сброс кэша SPI
CTL |= 0x100;                         // SPI_REQ: процессор забирает FIFO
while (!(STATUS & 0x100)) [0xC012001C] |= 1;   // ждать SPI_READY и не дать сработать сторожевому
CTL = 0x00180008;                     // база: CRC_EN | задержка 8 | SS
[0xC0140000] |= 1;                    // включить кэш
[0xC0140004] = 1; while ([0xC0140004] & 1);    // сброс кэша
CTL &= ~0x20; |= 0x20; &= ~0x10; |= 0x10;      // перезапуск FIFO
CTL &= ~0x2000;                       // RAND_TXEN выключить
CTL |= 0x1000; CTL &= ~0x8000;        // RAND_RXEN включить, снять паузу
CTL &= ~0x100; while (STATUS & 0x100);         // вернуть FIFO кэшу
```

И два пункта, которых в функции SDK нет, но без них ничего не читается:

* **снять бит 2 в `0xC0140000`** — иначе кэш работает в обход декодирования и отдаёт сырые байты;
* **рукопожатие `SPI_REQ`** обязательно: пока FIFO у процессора, кэш физически не может читать
  флеш и окно отдаёт одни `FF`.

## Загрузчики HWSC и FWSC

Две маленькие программы из SDK, которые штатный инструмент — и `upgrade.bin` — грузят в ОЗУ при
прошивке:

* **HWSC**, «hardware scan»: опрашивает SPI-флеш и возвращает JEDEC-идентификатор чипа.
* **FWSC**, «firmware scan» и драйвер записи: инициализируется, проверяет чип, затем пишет
  загрузочные записи и прошивку.

Обе грузятся по **одному адресу `0xbfc2c000`** и работают по очереди. HWSC вызывается со смещения 0,
инициализация FWSC — `+0x200`, драйвер записи — `+0x400`.

Инициализация FWSC попутно вычисляет геометрию: `строк = ёмкость / 66`, затем
`SPI0+0x20 = 0xC0140008 = строк × 64`, `0xC014000C = 0x003FFFC0`, `0xC0140000 |= 4`.

**Опасные места:**

* самый первый вызов драйвера записи FWSC **в любом режиме** стирает первые 64 КБ флеша, где лежат
  загрузочные записи. Пока не готовы писать — только инициализация;
* `NorFwsc.bin`, извлечённый из `AFI.bin`, при этом первом вызове стирает `0x0000`–`0xFFFF`, а при
  `header[2] == 2` стирает весь чип ещё на инициализации;
* загрузчик SDK кладёт BREC по логическому `0x400`, а MBREC **этого** устройства ищет его по
  `0xFC0` — см. `fix_brec_offset()` в `tools/adfu_flash.py`.
