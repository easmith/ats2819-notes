# Восстановление: как выглядит кирпич и как из него выйти

Написано после того, как наушники были сломаны записью и восстановлены.
[English version](../en/07-recovery.md).

## Окончательно убить его нельзя

Загрузочное ПЗУ — около 32 КБ по `0xbfc00000` — зашито в кремний. Если во флеше нет загрузки,
которую ПЗУ принимает, оно поднимается на USB как **`10d6:10d6`**, то есть в ADFU, и по нему можно
залить что угодно. Записью во флеш это состояние не портится.

| Что видно на USB | Что это значит |
|---|---|
| `10d6:10d6`, красный индикатор | ПЗУ не смогло запустить прошивку — во флеше нет пригодной загрузки |
| `10d6:1101` и диск `AGP-S22` | прошивка работает |
| ничего, красный индикатор | выключено и заряжается, **либо** глубокий разряд |

Последняя строка важна: исправные наушники, подключённые в выключенном состоянии, **не дают
никакого устройства на USB**. Это не поломка.

## Две найденные здесь причины

**1. Зерно рандомайзера.** Загрузчик SDK пишет с программным зерном 0, а загрузочное ПЗУ читает со
встроенным зерном чипа. Все контрольные суммы сходятся, содержимое побайтно верное — и ПЗУ всё
равно видит шум. Лечится одним словом по `0xBFC2C308` (`0x34794000` → `0x34790000`), которое
сбрасывает `RAND_SEL`, и пишущий механизм берёт зерно оттуда же, откуда ПЗУ. Это `use_hw_seed()` в
`tools/adfu_flash.py`, включено по умолчанию. Подробно — в
[02-flash-format.md](02-flash-format.md).

**2. Смещение BREC.** Загрузчик SDK кладёт BREC по логическому `0x400`, а LFI — после него; MBREC
этого устройства ищет BREC по `0xFC0`. Лечится `fix_brec_offset()`, которая перекодирует три
EXTEND'ованных непосредственных операнда по `0xBFC2F534/556/5D6`. Проверено по заводскому образу,
где `0x400`–`0xFBF` пусты, а BREC начинается с `0xFC0`.

Обе правки проверяются до того, как что-то уйдёт в устройство: `tools/loader_check.py` сверяет
загрузчик с той ревизией, к которой относятся эти адреса, и **громко предупреждает** при
расхождении, не отказываясь работать: репозиторий не может знать все сборки SDK, и решение — ваше.

## Процедура

Устройство в `10d6:10d6`:

```bash
# 1. сухой прогон: ADFUS + HWSC + инициализация FWSC, без записи
sudo .venv/bin/python tools/adfu_flash.py stock
#    ожидаем: flash id c84015, FWSC init status 0

# 2. запись заводского образа обратно
echo WRITE | sudo .venv/bin/python tools/adfu_flash.py stock --write --verify 0x5000
#    ожидаем: BREC ok, LFI ok, MBREC ok, ~8 с, 20480/20480 IDENTICAL

# 3. переподключить кабель; устройство должно загрузиться
```

Именно этот прогон вернул устройство к жизни 25 октября 2026 года: 8,1 с записи, переподключение —
и оно включилось, определилось как `10d6:1101` и смонтировало свой диск.

## Грабли, на которые здесь уже наступили

* **Побайтное чтение регистров врёт.** Команда ПЗУ `0x93` копирует память по байту, и 32-битный
  регистр отдаёт только младший байт. Регистры надо читать стабом, через `lw` (`--regs`).
* **Запись отображения 0 занята ПЗУ.** Чтение через «неиспользуемую» запись 9, направленную на тот
  же виртуальный адрес, даёт не те данные.
* **Рукопожатие `SPI_REQ` обязательно.** Пока FIFO у процессора (`CTL` бит 8), кэш не может читать
  флеш и окно отдаёт `FF`. Надо вернуть FIFO кэшу и дождаться снятия бита 8 в `STATUS`.
* **Бит 2 в `0xC0140000`.** Инициализация FWSC его ставит, и кэш обходит декодирование. Для чтения
  декодированных данных его надо снять.
* **Ошибка CRC на стёртой области — норма.** У пустых строк контрольные байты `FF FF`, они не
  совпадают ни с какой CRC. Сам флаг ничего не доказывает — сравнивайте байты.
* **После команды `OVER` нужно переподключение**, иначе устройство не отвечает на опрос ПЗУ.
  `start_adfus()` в этом случае переиспользует резидентный ADFUS, а не пишет поверх работающего кода.
* **Программно включённый ADFU заканчивается сам** на исправном устройстве, за секунды. Ловить
  «ловушкой», опрашивающей USB на `10d6:10d6`.
* **В ADFU не идёт зарядка.** Несколько часов в сервисном режиме посадили аккумулятор до
  срабатывания защиты, и помогла только долгая зарядка. Перед прошивкой заряжать до полного.
* **Первый вызов драйвера FWSC стирает первые 64 КБ** в любом режиме. Пока не собираетесь писать —
  только инициализация (`+0x200`), никогда драйвер (`+0x400`).

## Чему в этом репозитории можно верить

| Файл | Насколько можно верить |
|---|---|
| `firmware/stock/nor_logical_1MB.bin` | логический образ, все контрольные суммы сходятся, **и устройство из него восстановлено** — проверен делом |
| `firmware/raw/raw_first_1MB.bin` | сырое физическое чтение *работающего* устройства, снятое после восстановления. Перемешано встроенным зерном чипа, поэтому начинается с `17 61 ee cc`, а не с `86 53 df 0e` (зерно 0). Выровненность проверена: пустой логический диапазон `0x400`–`0xFC0` ложится ровно в пустой физический с шагом 66 байт |
| `firmware/prompts-ru-en/afi_plain.bin` | образ, который был прошит и проверен на устройстве |
| `tools/verify_raw.py`, `tools/norline.py` | полезны для работы с форматом, но **не** доказательство того, что образ загрузится |

Сырой эталон — та независимая мерка, которой проекту не хватало почти всё время: с ней любую
будущую запись можно сверить байт в байт, не полагаясь на собственную модель формата.
